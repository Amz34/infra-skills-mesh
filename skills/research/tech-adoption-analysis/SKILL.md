# Tech/Post → Infra-Fit Analysis

## When to Use
Trigger: Aamir shares a link (usually a `https://lnkd.in/p/<code>` LinkedIn post by AI influencers like Akshay Pachaar, or an `x.com/.../status/...` post) with "analyze this", "beneficial to our infra?", "how can our infra use this", or the older form "X ka fida hai?". He wants an expert read: what is it (verified), is it worth anything to HIS stack, and what to do NOW. Do not answer from the post's word alone.

Sub-classes, all in scope:

- **Mail-delivered AI newsletter / roundup** ("Expertly analyze the email; subject: … in `<acct>@gmail.com`") → N claims across N items instead of one artifact: ESP-dedup + identity, then a per-CLAIM verification table against vendor/leaderboard primary sources, then quantify for his economics and bucket into Act / Borrow / Watch / Ignore. Full recipe + the Sep-2026 voice-price bank: `references/ai-newsletter-verification.md`.
- **Vendor/product mail THREAD for a product we already audited** ("analyze the *jev jev jev*
  emails in `<acct>@gmail.com`", "is it useful for our infra?") → a **claim-DELTA audit**, not a
  first read. Reconstruct the whole lifecycle from the mailbox (consent → waitlist → account-ready
  → sign-in OTP → press/newsletter coverage), then re-verify **only the claims that were
  UNVERIFIABLE or 404 at the previous audit** and lead with what CHANGED. Worked case 2026-09-21:
  the 19-Sep audit's sole blocker ("the `cooksafe` benchmark isn't published → not independently
  reproducible") had silently cleared (now 0.1.0 on PyPI + pypi.typesafe.ai) — one delta + the
  account-ready mail together flipped the class from "watchlist" to "one 30-min test decides it".
  Recipe: `references/vendor-thread-claim-delta.md`.
- **Tool/repo/model post** → the workflow below (verify against primary sources, map to infra).
- **Free/heap API gateway pitch** ("free models", "10× cheaper than official", "one key all models") → run the recon ladder + verdict shape in `references/free-api-relay-due-diligence.md`, and give the **airlock design** so the reply isn't just "no".
- **Promo/playbook funnel** ("we booked 12 demos in 5 days with <new model>", a comment-gated LinkedIn post → Notion/Google doc "playbook" → trial/book-a-call). There is no repo and nothing to install; the deliverable is **funnel anatomy + cross-artifact number reconciliation + the $0 alternative**, not a summary. The doc is usually a JS shell — extract with the app's internal JSON API, not `web_extract`. Recipe: `references/promo-funnel-forensics.md` (signals/scripts get extracted so the tactic becomes ours; the hype layer gets labelled).
- **Concept/architecture post** (no repo to install — "harness vs orchestration", "why agents fail", "context engineering"). There is nothing to verify on GitHub, so the deliverable changes shape: (1) resolve + fetch the post **and read the comment thread** — on influencer posts the one practitioner comment is often worth more than the body (worked case: a commenter named the real failure mode — *systems fail in the seams; the missing layer is verification the agent did not write for itself* — which became an actual build); (2) verdict = what the thesis gets right **and what it omits**, each omission backed by a number from OUR box, not opinion; (3) map each missing layer to a concrete piece of our infra with a measured gap; (4) ranked leverage list (effort × value) + monetization readiness per play; (5) then build the cheapest high-value item **in the same session**. "Experty analyze" + "do QA ur self" is not a request for prose — the bar is a working artifact plus independent evidence. Verifier recipe: `agent-autonomy-governance` → `references/layer3-independent-verification.md`.
- **Reference-stack gap audit** ("analyze it, what gaps are there in OUR infra") — the link is a course/vendor landing page or an architecture diagram whose value is its **capability layers** (e.g. an AWS data-engineering masterclass: Core Infra → Compute & DB → IaC → Data Lake & Spark → Warehouse). There is nothing to install and no claim to verify; the deliverable is a **capability scorecard of OUR box against those layers**, every line carrying evidence off this host. Full recipe: `references/infra-gap-audit.md`; re-runnable probe: `scripts/infra_capability_audit.py`.
- **Reference stack = a live seminar/masterclass we attended or captured** ("is seminar se hamari infra me kya upgrade karna chahiye?"). Same scorecard deliverable, but the evidence source is a captured transcript and the axes come from the speaker's OWN taxonomy (worked case, DDS 2026-09-20: prompt → context → harness → **loop engineering**, plus 6 stages of an agentic app, ReAct, RAG-as-file-search-tool, 4 chunking strategies). Inventory the box first (MCP servers, RAG store + chunk params, skill/CLI surface, loop telemetry), then a `level | status | PROOF` table where the 🔴 row is the largest *measured* absence, a P0/P1/P2 with real paths/ports, and an explicit "deliberate non-upgrades" section. Recipe + the recurring findings on our box + deliverable shape: `references/seminar-to-stack-upgrade-audit.md`.
- **Gap audit → "implement karna faida hai?"** The follow-up question after a gap audit is not a restatement of the plan: it is a **phase-ROI decision audit** — per-phase verdict (DO NOW / DO subset / **OFFLOAD** / DEFER), a *measured* RAM bill of materials for the cheap lane, an offload lane for the heavy items (free notebooks instead of resident services), a promote-trigger per deferred phase, and an explicit refusal list (incl. the paid course when architecture is reproducible free). Recipe + measured numbers: `local-lakehouse-ops` → `references/phase-roi-decision-audit.md`.

## Workflow

1. **Resolve shortener FIRST.** Direct extraction of the `lnkd.in/p/` short URL can 500 (Firecrawl). `curl -sIL -A "<desktop UA>" "https://lnkd.in/p/CODE" | grep -iE '^(location|HTTP/)'` → canonical `linkedin.com/posts/<author>_<slug>-<id>/` URL.
2. **Fetch content** with `web_extract` on the canonical URL — guest LinkedIn post pages usually extract cleanly once resolved (title + full body + first-comment links come through). If blocked — or you only hold a bare `lnkd.in/<slug>` whose `curl -sIL` prints no `Location:` line — go straight to the reader proxy: `curl -s --max-time 45 "https://r.jina.ai/<url>"` returns the **full post text anonymously** (verified Sep 2026: `web_extract` gave ~700 chars of login chrome and the headless browser ~600 chars of the same, while the reader returned the whole post). Route table, char counts and citation provenance: `references/login-walled-social-posts.md`. Otherwise run the blocked-page-recovery ladder. **Long "top-N tools" listicle posts come back TRUNCATED mid-list** (middle items collapsed behind `...`) — the FULL post text lives in the `og:description` meta tag of the raw HTML: `curl -sL <canonical_url> -o /tmp/post.html` then regex `<meta[^>]+property="og:description"[^>]+content="([^"]*)"` → complete numbered list + every lnkd.in link, ready for per-repo resolution/verification.
3. **Verify claims against primary sources** (non-negotiable, even for a demo/hype post):
   - Repo reality check: `curl -s https://api.github.com/repos/{owner}/{repo}` → stargazers_count, license, language, created_at vs pushed_at (pushed recently = alive), description. Stars+MIT+active in weeks ≠ production-grade; say so.
   - Model claims: per-model endpoint `https://huggingface.co/api/models/{org}/{name}` → license (inside tags, e.g. `license:mit`), downloads, likes, siblings (LICENSE file present = real), pipeline tag; then `.../resolve/main/config.json` for architecture/size hints. HF org listing (`.../api/models?author=ORG`) when the exact repo name is unknown. **A model card is not a deployability verdict** — for any custom/experimental architecture run the ladder in `references/model-local-runnability-ladder.md`: HF `config.json` `architectures` → llama.cpp arch-support issue state → Ollama registry manifest → community GGUF quant sizes vs our 11.9GB RAM / no-GPU ceiling. **"GGUF quant files exist" ≠ "llama.cpp can run the architecture"** (community quants appear for arches whose support PR is still OPEN), and an empty `inferenceProviderMapping` = no HF serverless path either.
   - Paper claims: `curl -s "https://export.arxiv.org/api/query?search_query=all:{term}&max_results=5"` → parse `<entry>` title/id/published/authors — real title + date + author list = paper exists, and the author list reveals lineage (e.g. Song Han's MIT group + NVIDIA). **HTTPS only**: plain `http://export.arxiv.org` gets security-flagged (plain-HTTP download piped to an interpreter) and returns nothing.
4. **Map to Aamir's infra with CONCRETE equivalents** — name real pieces (Ollama qwen 7b/3b ceiling, hybrid_router+pii_gate = his router, Hermes skills = curated harness, cron no_agent scripts + monitor hash-suppression = computation-out-of-model, delegate_task, execute_code, web_extract head+tail+path). "Ye to humara X already karta hai" beats generic praise every time.
5. **Verdict in three buckets:** Adopt now (rare) / Borrow ideas only / Watchlist (with an explicit re-check trigger). Honest blockers first: hardware ceiling (VRAM of his local stack), token-overhead math at HIS task sizes, maturity (research checkpoint vs prod), integration cost. Note the meta-cost the post hides (e.g. harness generation happens before every task).
6. **Answer "abhi kya kare?"** — one concrete next action, or explicitly "kuch nahi — ye post hamare setup ka validation hai". Never invent work to look busy.

## Measure-on-hardware proof (decisive when the pitch IS a resource number)
If the post sells memory / latency / throughput / compression, README reading is not enough — install the candidate in a **throwaway venv** and measure it on THIS box. That is what turned the turbovec post into a verdict (numbers, baseline, and the reusable bench: `references/infra-baseline.md`).
1. Check the PyPI wheel tags first: `curl -s https://pypi.org/pypi/<pkg>/json`. A `manylinux*_aarch64` (or `py3-none-any`) wheel = **no Rust/C toolchain needed** on this ARM box. Then `python3 -m venv ~/.hermes/tmp/<tool>_venv && ~/.hermes/tmp/<tool>_venv/bin/pip -q install <tool> numpy` and confirm `import` works.
2. Size against HIS corpus, not the post's: locate the store (`find ~ -name "chroma.sqlite3"`) and grep the stack for the real embedding model/dim (`grep -rioE "bge-m3|mini-?lm|text-embedding-[a-z0-9-]+" ~/ai-stack/*.py`). bge-m3 = **1024-dim**, Chroma default = 384; the post's 1536/3072 are OpenAI's dims and never apply here.
3. Do the arithmetic on the actual saving: `vectors × dim × 4 bytes` float32 vs the claimed bit-width. **State the absolute number, not the multiplier** — "15× compression" sounds huge until it's 548 × 1024 × 4 ≈ 2.2 MB of savings.
4. Bench with **embedding-like data**: clustered then unit-normalized (per-centroid `rng.normal`), never uniform noise — uniform vectors give unrealistic recall and can make a working index look broken.
5. Write probes to a **file** (`write_file`) and run the file. Long inline `python3 - <<'PY'` heredocs that touch sqlite/gateway paths get refused by the terminal safety guard; the file form runs clean. Foreground cap is **600s** — N=50k / D=1536 / 1k queries finishes well inside it (K=500k does not: use `background=true`).
6. Close with the sandbox declaration: name the scratch venv path, state that `ai-stack` / prod was untouched, and offer to delete it. The verdict is still "no action" even though recon installed something.

## Response shape (Aamir preferences)
- Hinglish, concise, headers/bullets; structured facts with short labels. No hype, no filler praise.
- Always separate the post's claim from verified fact (repo stars/license/dates).
- Verdict symbols land well: ✅ adopt / ❌ not now (with reason) / 👀 watchlist.
- Cost-sensitive framing throughout — he runs token watchdogs; savings claims get checked against his short-task mix.

## Watchlist pattern: no_agent delta watchdog
When the verdict is "watch for X to mature" (smaller model variant, public API, distilled port), deploy a silent monthly **no_agent** cron instead of promising to remember:
- Generic template: `templates/delta_watch_noagent.py` (state-file delta detection).
- First run = baseline (silent); later runs print ONLY new findings → cron no_agent delivers stdout verbatim, empty = silent, zero tokens.
- Poll HF API (`.../api/models?author=ORG`, `?search=...`) + OpenRouter models API (`openrouter.ai/api/v1/models`) as the "public API exists" signal.
- Network errors → exit 0 silent (transient, not actionable).

- Verified example in the wild: cron job "JIT-Agent monthly watch" (schedule `0 9 1 * *`, script `~/.hermes/scripts/monthly_jit_agent_watch.py`).

## Pitfalls

- **A negative result measured on a SUBSTITUTE implementation is proxy-lane evidence — label it, always.** When the vendor key is missing and you test through a drop-in adapter / shadow copy / your own re-implementation, those numbers describe the stand-in's calibration, NOT the product. Write "unreproduced on our lanes via a proxy; real-key head-to-head pending" — never let it harden into "the vendor's benchmark is false". A later session reads the flat negative, quotes it as settled, and skips the decisive test that was only 30 minutes away. (Worked case: Jev decisions measured through `system-one-adapter` + DeepSeek; the real-key test was still pending at the time of writing.)
- **On a promo funnel, reconcile the numbers ACROSS artifacts first.** Post body, post image, doc title, doc body and vendor homepage are written by different people at different times and rarely agree (worked case: "10,000+ meetings" / "3000+ meetings" / "12 demos in 5 days" / a doc body whose own ramp needs 2–3 weeks — four artifacts, four numbers). Naming that mismatch in one sentence outweighs any amount of qualitative critique.
- **Comment-gated CTAs manufacture engagement — compare comments to reactions** (537 comments vs 172 reactions ≈ 1 reaction per comment) and label the count as engineered, not proof of value. Corollary: when the harshest comment is the **author's own** pinned/early comment, that is pre-emptive inoculation, not audience sentiment.
- **Never carry a price you could not reproduce.** If `/pricing` 404s on the apex domain (or 308s to a different product line than the one being pitched), write "pricing is not publicly comparable" — a figure obtained from an earlier scrape is not evidence.
- **Date a doc's screenshots before trusting its timeframe.** Filenames survive in the Notion block JSON (`Capture_decran_2025-09-25`, `Screenshot_2026-05-29`): assets older than the claimed result reclassify the doc as a marketing asset. Uniform 5-star replies with no losses = mockup; a real inbox/CRM shot shows rejections and low scores.
- **A model name in a title is not a product feature.** "…with Fable 5.1" turned out to be Anthropic's newly released Claude Fable 5.1 / Mythos 5.1 used as a hype hook — the name never appeared in the doc body. Web-search the model name before crediting it as an integration.
- **Separate the one durable primitive from the sales layer**, and say what is reproducible on our own stack at $0 (for outbound: signal-based prospecting — competitor engagement, new role/hire, fresh funding, niche-influencer follows, public pain points + ICP filters + warming + short DM scripts). That primitive is the part the user keeps.
- **Name the channel risk, don't just evaluate the product**: tactics that are platform-enforced against (mass-DM automation) endanger the user's own account, so recommend the half that is safe (signal detection + human-sent DMs) instead of a blanket trial.
- **Newsletter price claims often live inside an IMAGE, not the text.** Pull the CDN image (`media.beehiiv.com/...png`) and read it with `vision_analyze` asking for every number verbatim — verified case: GPT-Live-1's "~$3/hour, voice layer only, you pay for both" existed ONLY in the embedded image. Text-only reading misses the edition's most important figure.
- **A "$X/hour" for a voice/agent API is a FLOOR, not the total.** OpenAI's own live docs: billed per second, and "the backend model and tool usage are charged separately" — the voice layer is additive. Say so before quoting the price to a client.
- **Bot-walled vendor pricing ≠ dead end.** Vercel Security Checkpoint (reception.ai/pricing) and even `impfetch` can be blocked; fall back to the press article the newsletter cited and label the number *press-sourced / unverified* in the reply. Never upgrade an unverified price into a ✅.
- **Roundup counts drift faster than scores** (live page: "15 tasks / 193 runs" vs email's "215 tasks"; its scores were exact). Verify counts separately, and don't treat a wildly accurate roundup as primary research — it's a pointer.
- **Don't let "X is dead" framing doom his own business.** "Voice AI startups are ripped" = the horizontal API-wrapper layer; a vertical service+integration business (Sanad) is a different bracket. State the distinction explicitly.
- **A live capture has THREE sources that disagree — quote the one that said it.** In a recorded
  session the audio transcript, the audience chat and the slides each carry different claims, and
  the same product can have two names (verified 2026-09-20: the demo app is *HALA* on the slide
  and "Decobot" in the chat; "fixed-size will break your system" was never said — the slide reads
  "cuts sentences and table rows"). Before repeating a claim: grep the transcript for the exact
  phrase, then OCR the screenshots (`tesseract` over `shots/*.png`, one text dump you can grep).
  Attribute per source (`[src: transcript]` / `[src: chat]` / `[src: shot 090349.png]`), and when
  only a paraphrase exists, write "our reading, not his words". A plan built on a claim nobody
  made is worse than no plan. **Run `scripts/verify_capture_claims.py <run_dir> --claims "…" …`
  instead of hand-rolling the greps** — it OCRs `shots/*.png` into one dump, classifies each claim
  per source (VERBATIM / PARTIAL <ratio> / NOT FOUND), prints the timestamp or shot filename to
  cite, and ends with a verdict line (`slide-only` ⇒ never attribute it to the speaker;
  `paraphrase-only` ⇒ label it as our reading). Hand-written greps differ every session and the
  verdicts stop being comparable.
- **Identity facts from a live capture are claims too — including the speaker's own name/role.**
  ASR mangles proper nouns as readily as product names, and a wrong attribution poisons the whole
  deliverable (user correction, 2026-09-20: the host was Mohammad Arshad — "data scientist" —
  not the name the transcript first suggested). Verify who said it and what the vendor/product is
  instead, from the slide title, the session metadata (`label.txt`, `source-url.txt`) and the
  chat — and fix the source identity in the *report* the moment it is challenged, not just in the
  reply.
- Firecrawl 500 on the `lnkd.in/p/` short URL is NOT the page being blocked — resolve and retry the canonical URL before reaching for recovery ladders.
- **A concept post is not a tool verdict — don't force an install/test step.** When the post proposes no artifact, the verdict is "which layer of ours is thin + the number that proves it" (our own prompt-token bloat, gate-coverage %, spawn-depth ceiling), taken from `references/infra-baseline.md`. Tool-shopping language for a thesis post reads as filler, and "we already do X" only lands when X carries a measured figure.
- **"Do QA ur self" means artifact-level proof, not a claim of checking.** Run an independent check the worker did not author, prove it **can return FAIL** (inject a claim you know is false and show exit 1), record the honest failures *including your own* mid-session corrections, and put the numbers in the reply. Narrative QA ("I verified the output") is indistinguishable from trusting yourself — the whole point of the request is that the seams are where this class of work breaks.
- **A verbatim re-send is a deliverable-shape complaint, not a lost message.** Measured 2026-09-18: the identical "how can our infra systematically monetize this" ask arrived **five times** (the fifth with the post text pasted in). Each repeat meant the artifact was still too narrative. The move that closed it: deepen the ARTIFACT (4 → 10 gate rules, a real capability lane installed and measured, evidence file + binding report, one-command `run_all.sh` wired to the nightly suite) and lead the reply with measured numbers — never re-explain the previous answer and never treat the repeat as a duplicate to skip.
- **Influencer comment sections are half vendor pitch.** Take the practitioner insight (it often names the real failure mode), skip "DM me to scale your agents" replies, and never let a vendor's framing leak into the verdict or the build plan.
- **Repo org moves fake "dead repo" verdicts**: ggerganov's projects live under the `ggml-org` umbrella now (whisper.cpp, llama.cpp). GitHub API on the OLD owner returns None/empty fields — retry `ggml-org/{name}` or `search/repositories?q={name}` before judging a repo dead. Star counts quoted in posts verify close-to-exact once the API hits the right owner.
- Check the thing's overhead against HIS task sizes: per-task meta costs (harness gen, planning rollouts) eat savings when most tasks are short. Savings figures in posts are per-case on long-horizon tasks.
- Never propose installing research-stage runtimes on this box: 27B BF16 ≈ 55–60GB VRAM (TP=4) vs his Ollama 7b/3b. Flag the hardware ceiling immediately.
- If extraction of the same post is needed for HIS content engine, treat the post body as source material only after the analysis verdict — don't conflate "good for infra" with "good content".
- **t.co/lnkd.in are opaque** — resolve the real destination (`curl -sIL -o /dev/null -w '%{url_effective}\n' <short>`) before analyzing; the tweet's model list is marketing, not evidence. **When the header path yields nothing** — observed on a bare `lnkd.in/<slug>`: `curl -sIL` returned only `HTTP/2 200` with **no `Location:` line at all** — fetch the short-link page body instead and grep out the external URLs (`impfetch -o /tmp/lnk.html <short>` then grep `https?://` and drop linkedin/licdn/lnkd hosts). That is how the wrapper form `linkedin.com/safety/go/?url=<url-encoded lnkd.in>&urlhash=…&isSdui=true` resolved to the real landing page. The safety wrapper is a redirector, not a block — the target is usually still public.
- **A course/masterclass landing page is an upsell funnel — read it as one.** Education Ellipse's AWS masterclass had **zero price strings**: every CTA was "Register Now for FREE" followed by a WhatsApp-community redirect. Say that in one line and then take only its **syllabus layers** as the reference standard; the funnel is not a reason to skip the analysis, but the reply must not read like a course review.
- **A gap audit that lists only deficits misjudges the box.** Always include the section naming where OUR stack is *ahead* of the reference (agent ops: cron no_agent watchdogs, MCP system-of-record connectors, reviewed SKILL.md store, verify-ledger + autonomy registry — a data-engineering syllabus has no equivalent). Without it the user reads "we're behind at everything" and over-invests in a layer he doesn't monetize.
- **Recommend the free tier before any paid layer.** For cloud-DE gaps the cost-ordered ladder is: second Always-Free VM + `oci-cli` (`python3 -m venv` + `pip install oci-cli`, config already in `~/.oci`) for SPOF, Cloudflare R2 free 10 GB as the S3-compatible object tier, OpenTofu for IaC, DuckDB + Parquet on local free disk as the lake, Redis container for the queue — and **explicitly say to SKIP Spark/EMR/Redshift/Snowflake until a client pays for them**. He is cost-sensitive; an unpriced "adopt the whole ladder" answer is a failure.
- **"How much RAM will it take?" is answered by measurement, never by estimation.** On a box already holding ~8 GB (zram 5.0/5.8 GB consumed, 6.2 GB swap used, 15 client-critical services, 0 OOM in 14 days) a resident service competes with client gateways: run the candidate idle under a hard cap and read `docker stats`, and time the job with `/usr/bin/time -v` for max RSS before quoting any number (`local-lakehouse-ops` → `scripts/measure_footprint.sh`). Worked case: the whole light lakehouse lane (MinIO idle + Iceberg write + `dbt run`) measured **under 300 MB peak**, so the "obvious" shape resize turned out unnecessary — and the heavy framework lessons were offloaded to free notebooks instead.
- **SPA marketing sites return empty from `web_extract`** (2 lines of hero copy). Don't burn calls retrying — `curl -sL <domain>/sitemap.xml | grep -o '<loc>[^<]*'` maps the real feature surface, and search snippets carry the doc/limit numbers. Hidden routes exposed APInex's `/developers/airdrop` + `/developers/tools/solana`.
- **JS-rendered DOCS sites: skip the SPA shell, use `/llms.txt` then raw `.mdx`.** Verified on openui.com: `curl -sL https://<domain>/llms.txt` returns a ~20KB machine-readable doc map (every page + its canonical source URL), and each canonical `.../<page>.mdx` URL listed there returns **raw markdown with HTTP 200** — full doc text in one call, no browser, no Firecrawl. `/llms-full.txt` (~500KB) is the whole corpus when you need breadth. Use this for any docs-style tool (DSLs, SDKs, APIs) whose site fights `web_extract`; grep the downloaded file for the specific sections instead of re-fetching pages.
- **"Free/10× cheaper than official" is a verdict input, not a feature.** Official upstream cost sets the floor, so the answer is farmed/carded/shared keys or a subsidised crypto funnel — check the growth layer (airdrop/invite-and-earn/solana tooling) before believing the price.
- **An external gateway never becomes a default route.** Client-facing surfaces (Sanad/AVVS, bot tokens), PII, and leads are disqualified on the data-path line alone; write the sandbox airlock instead (see reference) and cap it with rate limiter + circuit breaker + quota ledger + kill switch.
- **"No action only advice" = change NOTHING** (no config, no alias, no key, no cron) and say so explicitly at the end of the reply. Read-only recon (whois/curl/sitemap/search) is still expected.
- **Recompute the post's own arithmetic — hype posts bundle the best compression with the best speed from DIFFERENT configs.** Worked case: "4-bit scalar quantization, 6,144 → 384 bytes, 16×" — 384 bytes is **2-bit** (4-bit = 768 B = 8×), and the quoted "3.4× faster than FAISS" is the **4-bit** number (2-bit averages only +23%). One sentence, two mutually-exclusive configs. Same pass: list what the post **omits** — recall delta vs the baseline (turbo-vec 4-bit trailed FAISS ~0.7pp R@1 at d=1536) and the omitted wins (O(1) remove: µs vs FAISS's 0.2–1.0 **seconds**). "Accurate-but-incomplete" is a category worth naming out loud.
- **Judge SIMD claims against ARM, not x86.** This box is aarch64 Neoverse-N1 with `asimd`+`asimddp` but **no `i8mm`/SMMLA** (`grep -c i8mm /proc/cpuinfo` → 0), so kernels fall back to SDOT and any "AVX-512 VNNI" line in a post is moot. Check `/proc/cpuinfo` flags before crediting a speedup claim, and say which kernel the box would actually take.
- **A vision/ML model linked for a product we ALREADY run is measured against that product's own component.** Run the released ONNX in the **product's own venv** (no new env, no torch), feed it the regions the existing detector already emits, and compare warm ms/frame with the detector's per-frame budget before saying anything about value. Sep 2026 worked case: an "any region – any relation, 20 ms/frame" relation head measured **1430 ms/frame vs the fire-watch detector's 181 ms** ⇒ the demo number is ~70x off on our box and the model is not frame-path code (async second stage on *confirmed* events, or shelf). Then split the licences: repo code Apache-2.0 + model-card licence `other` + a Meta-licensed backbone = **weights are not shippable** in a client deliverable however good the demo looks. Recipe, contract probe and verdict rules: `camera-vision-alert-consoles` → `references/third-party-vision-model-eval.md`.
- **"Few weeks old + many stars" ≠ production-ready, and it doesn't have to.** For a 1.0.0 with a real paper behind it, the honest verdict is often 👀 watchlist keyed to a **trigger in HIS data** ("corpus > ~500k chunks"), not "immature". Give the trigger explicitly so the re-check is mechanical.
- **Agent-skill marketplaces: review the extracted text, never the listing.** For `skills.sh` / `vercel-labs/skills` (and any "npm for agent skills"): `npx skills add -g` writes to the **real passwd home** and ignores an overridden `$HOME`, so a "fake HOME" sandbox still lands in the live `~/.hermes/skills` (observed; reverted). Use `npx skills use <owner/repo>@<skill>` instead — it prints the SKILL.md to stdout and installs nothing; wrapper + static risk pass: `~/ops/scripts/skills-review.sh` (run it on a known-bad case first to prove it can return a non-OK verdict). Hermes accepts a flat third-party skill immediately and marks it Trust=`local`, same as hand-written ones — no provenance distinction, so bulk `-g` installs dilute a curated store.
- **"Guidelines"-style skills are thin runtime-fetch wrappers, not rule sets.** Verified: vercel `web-design-guidelines` and `writing-guidelines` bodies contain **no rules** — they instruct the agent to WebFetch `raw.githubusercontent.com/...` on every run and state the fetched content "contains all the rules and output format instructions". So the audited artifact ≠ the executed artifact (Snyk/Socket/Gen audit the wrapper, the payload arrives later and can change upstream), and it is an indirect-prompt-injection path by design. Fix: fetch the payload once, read it, vendor it locally as a Hermes skill.
- **Leaderboard rank ≠ safe**: skills.sh `/audits` flagged vendor-owned repos too (microsoft `azure-validate` Critical, `azure-resource-visualizer` High; `xget`/`secure-linux-web-hosting` Critical; `use-my-browser`/`ui-ux-pro-max` High). Check `/audits` before recommending anything. Also: CLI telemetry is **on by default** (`DISABLE_TELEMETRY=1`), and `skills update` silently re-pulls content (weak version pinning) — treat installed third-party skills as unpinned dependencies inside a governance/verify-ledger stack.
- **`export.arxiv.org` API XML can return entries with empty author/date fields.** Fall back to the abstract HTML page and read its citation meta tags: `curl -sL https://arxiv.org/abs/<id>` then grep `citation_title|citation_author|citation_date`. That confirmed the TurboQuant paper (2504.19874) when the API parse came back hollow — a paper ID on its own is weak evidence; get title + date.

- **Benchmark at EQUAL corpus size or the comparison is an artifact.** Worked case 2026-09-21
  (HelixDB): first pass had the vendor engine holding 24 nodes vs our lane over 548 chunks — 4.1 ms
  vs 14.7 ms read like a 3.6x vendor win. After ingesting the full 548 into the vendor engine the same
  query set gave 11.39 ms, the win vanished, and per single retrieval call our lane was 5.9x faster
  (1.93 ms vs 11.39 ms). Ingest the engine under test to parity with the corpus it competes against
  before timing anything, and check the scaling direction (24->548 nodes took it 4.1 -> 11.39 ms).
- **A "check it yourself" verdict needs a checker that can FAIL, and every field it parses needs a
  regex-level review against the REAL log line.** Same case: the node-count extractor
  `(?:final )?count[^0-9]{0,40}(\d+)` matched `final count: (200, '{"c":548}')` and returned **200** —
  the HTTP status — which would have produced a confident false FAIL on the exact number the verdict
  headlined. Strip the `(status, body)` tuple before scanning, prefer the key named in the query's
  return clause, and return None (=> UNVERIFIED) instead of guessing when the line is ambiguous.
- **Claims must be transcribed BY HAND from the artifact — never auto-generated from the same
  evidence the checker reads.** A claims file derived from the evidence makes the check circular: it
  always passes and proves nothing. The gap between "what the verdict states" and "what the raw logs
  show" is the entire product.
- **Drive the checker through all three paths on a hermetic fixture before pointing it at live data**:
  hand-known values for PASS (exit 0), one injected false claim for FAIL (exit 1 — and assert exactly
  ONE row is flagged, and that it is the injected key), and a partial fixture for UNVERIFIED (exit 2).
  Keep that self-test beside the checker (`~/ops/verify/helixdb_check_selftest.py`) as a regression
  guard. Do not grep the word "FAIL" to count failures — `FAIL=1` / `RESULT: FAIL` summary lines match
  too; parse the summary counters.
- **Archive the raw evidence next to the verdict and re-run the check against the ARCHIVE before
  deleting scratch** — it proves the verdict stays auditable after cleanup (worked: 8 MB bundle at
  `~/ops/kb/tech-adoption/evidence-2026-09-21/`, archived docs + logs + check transcripts, recheck
  exit 0). Also re-measure the footprint AFTER the full ingest: an idle sample (11.62 MiB) exists
  alongside the loaded peak (77.23 MiB) and the max is what the claim must be tested against.
